# Unified Codebase Analysis Report: dev-harness

**Project**: `/Users/claw/Projects/dev-harness`  
**Overall health**: **Fair** – Significant structural and operational risks undermine a well-intentioned architecture.  
**Analysis date:** 2025-07-03 (synthetic)

---

## Executive Summary

The `dev-harness` codebase is a capable and ambitious agent‑orchestration platform. It coordinates AI agents through structured, gated workflows, manages engagement lifecycles, and supports pluggable LLM backends. Documentation is excellent (README, CONTRIBUTING.md, docstrings), the test suite is large (1826 tests), and the architecture has a clear functional decomposition.

However, the project has evolved into a **flat, tightly‑coupled monolith** where business logic lives in UI‑layer CLI handlers, lazy imports mask real circular dependencies, and critical integration paths are barely tested. Two **high‑risk security vulnerabilities** (command injection in the `/exec` interactive command) and several **silent production bugs** (provider configuration asymmetry, a permanently broken `/consult` command) are present. Together, these issues indicate that the current velocity of feature addition has outpaced structural discipline. The codebase is not in crisis, but without deliberate refactoring, future changes will become increasingly expensive and risky.

---

## Key Findings Across Dimensions

### 1. Architectural Decay and Coupling

- **Flat architecture, no layer isolation**: The project is organised by functional package (`agents/`, `analysis/`, `session/`, …), not by architectural layer. Every module imports from every other. The architecture critic rates the pattern **“flat” with high confidence**.  
- **God modules**: `cli.py` (~2500 lines) has excessive fan‑out to 15+ subpackages and contains **~1000 lines of business logic** (engagement creation, snapshot manipulation, assessment parsing). `session/loop.py` (~1400 lines) couples 6+ boundaries and mixes UI, orchestration, and business rules.  
- **Circular dependency**: `agents/runner.py` ↔ `agents/cycle.py` is a real cycle masked by a lazy import inside `CycleRunner._run_step()`. If ever moved to module level it would deadlock the import.  
- **Boundary violations**: `Agents/runner.py` directly imports infrastructure config (`harness.config.provider_registry`) and filesystem paths. `state/temporal_worker.py` directly imports `temporalio` workflow definitions without an abstraction.  
- **Consequence**: All pieces are deeply entangled, making isolated testing and replacement impossible. Any change to the CLI risks breaking agent pipelines, engagement lifecycle, or analysis.

### 2. Critical Functional Bugs (Silent Failures)

From the **critical reviewer** analysis, three bugs are silently degrading functionality:

- **Provider serialisation asymmetry** (`type` vs `provider` key): `ProviderConfig.to_resolved_dict()` emits `type`, but `ApiBackend.run()` reads `provider`. This silently breaks Anthropic/Google tool‑format conversion and formatter selection – **these backend features are never activated** through the resolved config path.  
- **Phantom role `'architect-critic'`**: Defined in cycle definitions and fleets but **missing from the `AgentRole` enum**. When dispatched, `AgentRunner._attach_repo_tool()` raises `ValueError`, silently skipping RepoTool attachment.  
- **Broken `/consult` command**: The command router returns a sentinel `'__do_consult__'` that is **never handled** by the interactive loop – the command does nothing in chat mode.

### 3. Security Vulnerabilities

- **Critical (2x)**: Both the `harness/shell/repl.py` and `harness/session/commands.py` `/exec` command use `subprocess.run(…, shell=True)` with **unsanitised user input**. This allows arbitrary shell command injection (e.g., `; rm -rf /`).  
- **Medium**: The Temporal dev server database is world‑readable/writable in `/tmp`. Insecure permissions on multi‑user systems could expose workflow state.  
- **Low**: Hardcoded deep‑provider defaults and a spoofed User‑Agent may violate terms of service.  
- **Note**: The code‑critic also flagged multiple bare `except Exception: pass` blocks (in CLI, git operations) that suppress errors, making debugging and incident response harder.

### 4. Testing Gaps

The test suite is **extensive but defensive**: 74% coverage overall, but **the most critical, largest modules are virtually untested**.  
- `cli.py` – **17% coverage** (1299 stmts). The entire user‑facing command surface lacks integration tests.  
- `session/loop.py` – **38% coverage**. The interactive REPL loop’s IO‑heavy paths are untested.  
- `agents/runner.py` – **36% coverage**. Central agent orchestration tested only through extracted pure functions.  
- The suite is dominated by unit tests on dataclasses and pure functions; **genuine business‑feature tests (e.g., engagement life‑cycle end‑to‑end) are absent**.  
- Severe mocking overuse (e.g., entire pipelines mocked, never tested for real data flow).

### 5. Code Hygiene and Redundancy

- **Redundancy**: The tool‑calling loop in `api_backend.py` is duplicated in `run()` and `run_stream()`; from‑dict patterns are copy‑pasted across four config classes; slug‑resolution boilerplate repeats 10+ times in CLI handlers.  
- **Magic values**: API endpoint, model, timeout defaults are hardcoded in source; convergence keywords appear in two places.  
- **Error handling**: Bare `except Exception: pass` (5+ instances) and a fragile `"data" in locals()` check in `api_backend.py` after a loop.  
- **Documentation**: Excellent docstrings but **no formal API docs** (no Sphinx/mkdocs). The README references a non‑existent `harness observe` command (real name `inspect`).

## Recommendations

Based on the cross‑cutting analysis, the following actions will yield the highest return in stability, security, and future velocity.

### 1. Harden and Test the Interactive Shell (Immediate)
- **Fix command injection**: Remove `shell=True` and use list‑based subprocess calls. Add input sanitisation.  
- **Wire the `/consult` command**: Implement the `__do_consult__` handler in `_execute_common_effects()`.  
- **Fix the provider type key**: Standardise on `'type'` across all modules and add a unit test that validates `to_resolved_dict()` output against `ApiBackend.run()` consumption.  
- **Add integration tests** for the interactive chat loop using a scripted backend to cover these paths and prevent regression.

### 2. Extract Business Logic from `cli.py` and `session/loop.py`
- Create a **service layer** (`harness/services/` or similar) with dedicated modules for engagement creation, snapshot management, assessment parsing, and phase transitions.  
- Refactor `cli.py` to delegate to these services, keeping only Click‑specific argument handling and output formatting.  
- Decompose `session/loop.py`: extract consultation, phase‑jump, and context‑building logic into separate modules.  
- **Enforce a rule**: any new feature touching these god‑modules must extract at least one responsibility to a new module.

### 3. Break the `runner` ↔ `cycle` Circular Dependency
- Introduce a protocol (ABC or typing.Protocol) `AgentDispatcher` in a shared `core` or `protocols` package that `cycle.py` depends on, and `runner.py` implements.  
- Promote shared types (`AgentRole`, `ContextPacket`, `CycleStep`, etc.) to this dependency‑free core.  
- This will also enable cleaner testing of the cycle engine without mocking the real runner.

### 4. Raise Integration Test Coverage for Critical Paths
- **CLI coverage**: Use Click’s `CliRunner` to test every command with synthetic project directories – no network needed.  
- **AgentRunner backend**: Create a stub backend that returns predetermined responses to exercise resolution, fallback chains, and critic loops.  
- **Business‑feature integration**: At least one end‑to‑end test that runs `harness init`, creates an engagement, progresses through a phase cycle with a scripted backend, and verifies expected artefact/output.  
- Increase coverage threshold from 70% to 80% once the large modules are covered; add a `slow` marker for integration tests that use real I/O but no external services.

### 5. Strengthen Architectural Boundaries and Safety
- **Apply the project’s own architecture goals to itself** — define allowed dependencies between packages in a `harness-architecture.yaml` and enforce in CI via the existing conformance machinery.  
- **File locking for active‑engagements.yaml**: use `fcntl.flock`/`portalocker` or atomic write (write temp, then `os.replace`).  
- **Temporal database security**: move the dev‑server DB to a user‑specific directory with `0o600` permissions.  
- **Remove bare excepts**: mandate logging at debug level and add a lint rule that forbids `except Exception: pass` without justification.  
- **Consolidate duplicated configuration logic** (provider resolution, slug verification, path constants) to a single source of truth.

---

By addressing these five areas — security hardening, service extraction, cyclic dependency removal, integration testing, and boundary enforcement — the project can transition from a capable but brittle monolith to a resilient, maintainable platform ready for continued growth. The excellent documentation and clear purpose provide a strong foundation; the immediate need is to align the implementation with the architectural vision it already describes for its users.
