# Unified Codebase Analysis Report

## Executive Summary
The **dev-harness** codebase is a monolithic Python CLI tool for AI-powered agent orchestration. While its functional purpose is clearly fulfilled and supported by a solid battery of unit tests (1,800+ cases), the codebase suffers from **architectural flatness, tight coupling, and a “god module” CLI** that undermines maintainability, testability, and long-term evolution. Test coverage for the most critical behavioural paths – CLI commands, agent runner orchestration, session loops, and Temporal workflows – is dangerously low (17–38%), leaving the system’s actual runtime behaviour largely unverified. Several **medium-severity security issues** (unverified binary downloads, environment leak) and **pervasive bare exception handling** further degrade robustness. The project would benefit from a deliberate, incremental architectural refactoring to introduce ports-and-adapters boundaries, break circular dependencies, and raise test coverage on the system’s core orchestration paths.

## Connected Findings
The agents’ reports reveal multiple interconnected weaknesses that compound each other:

- **God‑module CLI → untestability & low coverage**  
  `cli.py` (1500+ lines) mixes presentation, business logic, and infrastructure calls (git, Temporal, subprocess). The test-auditor confirms CLI coverage is only 17%. Without split command modules or dependency inversion, any CLI change risks regressions that cannot be caught by a CI suite.

- **Circular dependencies → fragile orchestration & mocking pain**  
  `agents/runner.py` ↔ `agents/cycle.py` (lazy import to break the cycle) and `state/temporal_worker.py` ↔ `workflows/activities.py` create bidirectional coupling. This forces over‑mocking in tests (e.g., `test_wave_cycle.py` mocks entire subsystems) and makes it impossible to test the orchestration in isolation.

- **No infrastructure boundaries → leaked concerns & security risks**  
  Modules like `agents/cycle.py` and `wave/wave_cycle.py` directly spawn subprocesses; `cli.py` calls `harness.scm.git` and `harness.state.temporal_server` without abstraction. This not only violates separation of concerns but also embeds security-sensitive operations (e.g., downloading and executing a binary without integrity verification, `cli_backend.py` forwarding the full environment to subprocesses) deep inside business‑logic layers.

- **Sparse error handling → silent failures & degraded reliability**  
  Multiple `except Exception: pass` blocks in `cli.py` swallow critical errors, and the broad `except Exception` wrap in `init` loses stack traces. Coupled with low test coverage, these silent failure points are likely to manifest in production without detection.

The degraded documentation review (only the README was evaluated as “good”) means we lack systematic insight into in‑code and user‑facing documentation quality; this gap should be addressed separately.

## Prioritised Issues

1. **Security: Unverified binary downloads (Medium)**  
   - Temporal CLI downloaded via HTTP without any checksum or signature verification (`temporal_server.py`, Makefile).  
   - A compromised artifact would run with full user privileges.

2. **Testability: Critical coverage gaps in the behavioural core**  
   - CLI (17%), session loop (38%), agent runner (36%), API backend (59%), cycle engine (61%) – the system’s operational heart is essentially untested.  
   - No end‑to‑end tests exist at all, preventing validation of composed behaviour.

3. **Architecture: Circular dependencies & monolithic design**  
   - `runner` ↔ `cycle`, `state` ↔ `workflows`, and transitive loops through `session.loop` make refactoring risky and testability poor.  
   - `cli.py` fan‑out to 18+ modules acts as a maintenance bottleneck and prevents isolated testing of command handlers.

4. **Error handling: Bare `except Exception` throughout**  
   - `cli.py` features multiple `except Exception: pass` blocks; the `init` command hides precise failure causes.  
   - This pattern introduces silent failure modes and increases debugging time.

5. **Dependency hygiene: Unused packages**  
   - `aiofiles`, `jinja2`, and `rich` are declared but unused, adding unnecessary package size and confusion.

## Recommendations

1. **Enforce integrity checks for downloaded binaries**  
   - Add SHA‑256 verification to `download_temporal()` and the Makefile target. Hardcode the expected hash (updated on version bumps) or validate via a separate channel.  
   - This directly addresses the most immediate security vulnerability.

2. **Introduce ports-and-adapters to decouple infrastructure**  
   - Start with the CLI: split `cli.py` into per‑command modules (e.g., `cli/engagement.py`, `cli/fleet.py`) and define abstract interfaces for Git operations, Temporal client, and test runners.  
   - Move subprocess execution out of `agents/cycle.py` and `wave/wave_cycle.py` into dedicated adapter classes behind interfaces, enabling mocking and proper separation of concerns.  
   - This will simultaneously improve testability (paving the way for integration tests) and reduce coupling.

3. **Break circular dependencies with a shared data‑types module**  
   - Extract `ContextPacket`, `CycleStep`, `CycleResult`, `BackendResult`, and other common contracts into a new `harness.types` module.  
   - Both `runner.py` and `cycle.py` should depend on `harness.types`, not on each other. This eliminates the lazy‑import workaround and simplifies unit testing of pure logic.

4. **Replace bare exception handling with specific error types**  
   - Audit all `except Exception: pass` occurrences; replace with `except (subprocess.CalledProcessError, OSError, ...)` and always log the exception (`logger.exception()`).  
   - For non‑critical best‑effort tasks, catch only the expected failure types and explicitly chain errors where relevant.

5. **Establish an integration‑test strategy and raise core coverage**  
   - Add at least integration tests for the CLI commands (using `CliRunner` with isolated test directories) and async integration tests for `AgentRunner` and `CycleRunner` with real backends mocks exercising the full loop.  
   - Introduce a few end‑to‑end smoke tests that exercise the `engage` workflow in a sandboxed project.  
   - Set coverage thresholds (e.g., 80%) for the most critical modules (`cli`, `agents.runner`, `agents.cycle`, `session.loop`) to prevent regression.

These actions, incrementally applied, will transform the codebase from a fragile monolith into a well‑structured, test‑backed, and maintainable orchestration tool.
